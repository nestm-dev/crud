# `@nestm/crud-drizzle`

PostgreSQL-first Drizzle ORM 0.45 adapter for [`@nestm/crud`](../crud). Neutral
CRUD predicates compile to Drizzle SQL expressions, so values remain bound
parameters. Transactions and database-client lifecycle remain under application
control.

The `0.1` alpha is certified for PostgreSQL only.

```sh
pnpm add @nestm/crud@alpha @nestm/crud-drizzle@alpha drizzle-orm pg
```

```ts
import { bindDrizzleCrud, createDrizzleCrudAdapter } from "@nestm/crud-drizzle";

const usersAdapter = createDrizzleCrudAdapter({
	database: db,
	table: usersTable,
	columns: {
		id: usersTable.id,
		email: usersTable.email,
		createdAt: usersTable.createdAt,
	},
});

const usersBinding = bindDrizzleCrud({
	resource: users,
	fields: ["id", "email", "createdAt"],
	adapter: { useValue: usersAdapter },
	mappings: {
		create: (input) => input,
		update: (input) => input,
		// Maps framework-generated soft-delete and explicit scope update values.
		persistence: (values) => values,
		response: (record, relations) => ({ ...record, ...relations }),
	},
});
```

`columns` maps every CRUD logical field to its Drizzle table column; use
`recordKeys` when a returned row key differs from the logical field.
`mappings.persistence` handles logical values generated by soft deletion and
explicit scope `updateValues`, independently from API create/update mappings.

Required insert columns owned by a CRUD scope are declared explicitly. The
tuple changes only the create-mapper input boundary; the Drizzle adapter still
receives its complete inferred insert model:

```ts
const documentsBinding = bindDrizzleCrud({
	resource: documentsResource,
	adapter: { useValue: documentsAdapter },
	fields: ["id", "organizationId", "ownerId", "title"],
	scopeCreateFields: ["organizationId", "ownerId"],
	mappings: {
		create: (input) => ({ title: input.title }),
		scopeCreate: (values) => {
			if (typeof values.organizationId !== "string" || typeof values.ownerId !== "string") {
				throw new TypeError("The document scope did not resolve create ownership.");
			}
			return { organizationId: values.organizationId, ownerId: values.ownerId };
		},
		update: (input) => input,
		persistence: () => ({}),
		response: (record) => record,
	},
});
```

Bindings without `scopeCreateFields` remain strict and must return every
required Drizzle insert property. Let `create` use its contextual return type,
or explicitly annotate it with
`CrudCreateMappingValues<DocumentInsert, "organizationId" | "ownerId">` from
`@nestm/crud/adapter`.

The Drizzle adapter does not yet advertise the core atomic-upsert capability.
Although `bindDrizzleCrud` forwards generic binding metadata for custom capable
adapters, the bundled adapter rejects resources that enable `upsert` until its
PostgreSQL conflict-update authorization path is certified.

## Application-owned transactions and native row policy

Use `transactionRunner` when every standalone CRUD statement must execute in an
application-owned transaction, such as a transaction that installs a local
PostgreSQL RLS setting. The runner must honor the requested access mode and
isolation level and pass the transaction-scoped Drizzle database to the work:

```ts
const documentsAdapter = createDrizzleCrudAdapter({
	database: db,
	table: documents,
	columns: {
		id: documents.id,
		organizationId: documents.organizationId,
		ownerId: documents.ownerId,
	},
	transactionRunner: {
		run: (context, workWithTransaction) =>
			tenantTransactions.transaction(
				(transaction) =>
					workWithTransaction(transaction, {
						accessMode: context.accessMode,
						isolationLevel: context.isolationLevel,
						ownsCommit: context.mustOwnCommit,
					}),
				{
					accessMode: context.accessMode,
					isolationLevel: context.isolationLevel,
					propagation: context.mustOwnCommit ? "reject" : "required",
				},
			),
	},
	rowPredicate: {
		resolve: ({ table, context }) => authorizationPredicate(context.executionContext, table),
		transaction: { isolationLevel: "repeatable read" },
	},
});
```

`mustOwnCommit` is true for mutations. A runner must then open and own the real
transaction commit; joining an ambient transaction or resolving after only a
savepoint would make CRUD's `afterCommit` hook untruthful. Runners that
strengthen the requested isolation should report their effective state through
the callback's second argument. The adapter validates reported access,
isolation, and commit ownership before executing CRUD work. Omitting the second
argument retains the legacy contract that the runner used the requested state
and owns its transaction.

With a runner configured, bare reads and mutations self-enter it; operations
already carrying this adapter's active session reuse that session. Counted lists
request a read-only, repeatable-read transaction, and their rows and total use
the same resolved SQL expression in that transaction. Without a custom runner,
the adapter opens its own transaction for a configured row predicate and its
own repeatable-read transaction for counted lists.

`rowPredicate` is resolved inside the active transaction and combined with the
neutral CRUD predicate for find-one, list/count, update, and delete. It may be
asynchronous, but it must return a Drizzle `SQL` expression; a missing result
fails before the statement is issued. Inserts deliberately do not use it and
remain governed by CRUD scopes, collection authorization, constraints, and RLS.
Use the object form's `transaction.isolationLevel` when predicate resolution
loads snapshot-sensitive policy data; the requirement is applied before the
transaction opens and is accurately recorded in nested session checks.

`rowPredicate.transaction` covers only predicate resolution and application.
When a scope, lifecycle hook, validator, mapping, or projection also requires a
stable snapshot—including during create—declare an operation-wide minimum:

```ts
const documentsAdapter = createDrizzleCrudAdapter({
	database: db,
	table: documents,
	columns: { id: documents.id, organizationId: documents.organizationId },
	transaction: { isolationLevel: "repeatable read" },
	transactionRunner: tenantTransactionRunner,
});
```

The adapter requests the strongest operation, count, and row-predicate
isolation before any statement runs. Without a custom runner, configuring the
operation requirement makes the adapter open its own transaction. A runner
that reports weaker effective isolation fails closed.

The binder accepts Nest `useValue`, `useClass`, `useExisting`, and `useFactory`
adapter providers. Use a factory when another Nest module provides the Drizzle
database. The package never creates a driver, opens a pool, or closes a database
connection.

Unique PostgreSQL violations map to `409`, other database constraints to `400`,
and unrecognized failures to a sanitized `500`. Serialization (`40001`) and
deadlock (`40P01`) failures are retryable conflict errors; the adapter does not
retry them because lifecycle hooks may have external side effects. The `0.1`
alpha is not certified for non-PostgreSQL Drizzle dialects.
